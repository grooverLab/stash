Installing 590 Claude Code skills made Claude blind

grooverLab · July 2026 · 7 min read

Last week I went on a skill-collecting binge. Trading, investing, marketing, accounting, compliance, engineering - eleven domains, four research agents running in parallel, provenance checks on every repo. By Tuesday night I had 590 skills installed in ~/.claude/skills/. It felt like owning a library.

By Wednesday, Claude had stopped using most of them. Ever wonder why a skill you definitely installed never triggers? I found out the hard way: Claude Code context bloat is not about your conversation - it starts in the skill listing itself.

The part nobody tells you

Claude Code loads every skill in the global directory into every session. Each skill contributes one line - its name and description - to a listing in the system prompt. That listing has a budget: roughly 1% of the context window.

Blow past the budget and Claude Code does not complain. It quietly truncates. Descriptions shrink, then vanish. The overflow renders as bare names.

Here is why that matters. Auto-triggering - the thing that makes skills feel magical - runs on descriptions. When I ask "is my COT positioning crowded on gold futures," Claude matches those words against skill descriptions and pulls in cot-contrarian-detector. Strip the description and the match dies. A name-only skill is a book with the spine label ripped off.

So the paradox: every skill I installed made Claude a little more blind. The budget stays fixed. The descriptions competing for it grow. The more I owned, the less Claude could see. My trading sessions carried churn-prevention and popup-cro with full descriptions while backtest-expert sat nameless in the overflow.

The fixes that don't fix

Deleting skills works, but you lose them everywhere, and I had just spent tokens finding them. skillOverrides in settings.json can demote skills, but it takes one key per skill - no globs - and hand-maintaining 471 entries is a punishment. Plugins scope cleanly, but only for skills packaged as plugins; most of a hoard is not.

The insight that unlocked it came from reading how discovery actually works: Claude Code scans exactly two places for directory skills. The global dir, and the current project's .claude/skills/. That's the whole mechanism. And symlinks count.

Shelves

So I stopped treating ~/.claude/skills/ as a warehouse and built an actual warehouse next to it:

~/.claude/skill-profiles/     the warehouse - loads nowhere by itself
  trading/  marketing/  db/ ...
~/.claude/skills/             global - the 53 I want everywhere
<project>/.claude/skills/     per-project symlinks - the selection

A picker (terminal TUI or a browser page served by a one-shot nc) shows the warehouse as a tree. Toggle profiles or single skills, press enter: a diff engine links what you checked, unlinks what you didn't, never touches a real file, and launches claude. My trading project loads about 130 skills now. The marketing project loads 50 different ones. Every loaded skill keeps its full description, because the listing finally fits its budget.

Two shell scripts. No daemon, no database, no LLM in the loop, nothing to re-install - updates are a git pull away because everything is symlinks.

I called it stash.

Was any of this hard? Not the code. The hard part was noticing the problem at all, because blindness by truncation never throws an error.

The part where agents surprised me

Once the warehouse existed, an obvious idea followed: a tiny skill called /stash that lets Claude load skills just-in-time. Three steps: extract what the task needs (video, backtest, hiring plan), grep a generated index of every skill's description, link and load the winner. The index is a TSV; the whole skill is under fifty lines.

Testing it taught me more than building it.

I spawned an agent with only this: /stash we are about to launch this project publicly and I want a short shareable launch video for it. No paths, no hints. The agent found the skill file, read its frontmatter, saw it was marked user-invoked-only, and decided that meant it should walk past - then built the video with a completely different tool it happened to know. Technically defensible. Completely not what I wanted.

The fix was one paragraph added to the skill: if the literal text /stash appears in your instructions, the user already invoked you; the lock only bars you from showing up uninvited. Second test, same prompt, byte for byte: the agent ran the funnel, grepped the index for "video", got four candidates across two domains, picked the launch-video skill on its description, linked it from the warehouse, and shipped a 24-second video with a soundtrack.

Instructions ask. Mechanisms enforce. I keep re-learning that one.

There was a second lesson in the grep itself. My first funnel design said "pick the domain, then browse it" - and a launch video task never says marketing. Searching by the deliverable across all domains fixed it. The index descriptions already contained the word "video"; I had just been grepping the wrong axis.

What I can't claim

stash is macOS-first (Linux needs openbsd-netcat for the browser picker). The migration rules that sort a flat skills directory into domains shipped tuned to my repos - you'll edit one case statement or build profiles by hand. And per-project loading cannot fix a skill whose description is bad; it just makes sure the description survives.

The blindness problem, though - that one compounds quietly in every setup that hoards skills globally, and it will not announce itself. Check your own session: if your skill listing shows name-only entries, you're past the budget already.
